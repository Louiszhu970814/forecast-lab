## 目標

M2 的 `scheduler.py` 只處理預先固定的題集（campaign）。M3 需要無人值守地持續運作：每 10 分鐘查詢新題、處理題目修訂、把工作排進佇列、執行，再交給 `submit.py`。本工作提供這個「一個週期」的入口與 macOS 的排程包裝，但**不安裝**任何排程：安裝由 Louis 在核准 `trial` 後手動進行。

## 規格

1. **`src/cycle.py`**：執行一個週期後結束，供 launchd 每 10 分鐘呼叫一次。
   - 先取得全域鎖；上一個週期還在執行就直接結束並記錄（不排隊、不等待）。
   - 依序：檢查停用開關（`config/STOP_SUBMIT` 只影響送出；`players_enabled` 影響各線）→ 輪詢允許的場地（沿用 `poll_questions.py` 的函式，不另寫一套 API 呼叫）→ 依新快照更新工作佇列 → 在本週期的時間上限內執行排程器 → 呼叫 `submit.py run`。
   - 執行前檢查沿用既有的 preflight（CLI 版本、全域基準、驗收、額度）；任一線不通過就只停那一線，並記錄原因。
   - 每個週期追加一筆紀錄到 `data/cycles.jsonl`：開始與結束時間、每一步的結果、新題與修訂題的 ID、各線狀態、錯誤。
2. **持續題集**：把 M2 固定題集的機制延伸為「依輪詢結果持續加入新題」的模式。現有固定題集的行為與測試必須保持不變；新模式的預算窗口與上限沿用 `budget.py`，不得自行放寬保留線或上限。
3. **題目修訂**（§3.2、D53）：已抓到但尚未送出的題目出現新快照時：
   - 結算條件、標題或選項有實質變更：舊快照尚未採用的結果作廢；截止時間允許時，以新快照重新排入第 1 層；
   - 來不及重跑時：題型、選項或截止時間改變 → 不送出；只有文字修訂 → 允許送出舊快照的結果，但紀錄要標記修訂、維持綁定舊快照；
   - 已送出的題目再變更：只記錄，不重新送出。
   - 作廢與重新排入都要以追加紀錄表示，不改寫舊紀錄。
4. **launchd 包裝**（放在 `launchd/`，不安裝）：
   - 每 10 分鐘執行一次的 plist 範本，以 `caffeinate -i` 包住包裝腳本；另提供每天 21:00（台北時間）抓取結算與每週一 21:00 產生報告的 plist 範本（目標程式還不存在的，範本中保留並註明待 M3 後續工作）。
   - 包裝腳本設定工作目錄、使用 `.venv` 的 Python、把 stdout／stderr 寫到 `data/logs/`，不在命令列或 plist 中放入任何機密。
   - `launchd/README.md` 說明 Louis 如何安裝、檢查與移除；註明安裝前須完成的核准。
5. **時間上限**：一個週期的執行時間不得超過下一個週期的開始時間減去安全餘裕；超過時停止接新工作，等待中的工作留到下一個週期，並遵守 §3.5 的決策截止點。

## 驗收條件

- 單元測試（假的 API 回應、假 adapter、假時鐘）涵蓋：上一個週期仍在執行時直接結束；新題加入佇列；三種修訂情形的處理與「已送出後再修訂只記錄」；停用開關與單線停用；preflight 不通過只停該線；週期時間上限；`cycles.jsonl` 的紀錄；M2 固定題集的既有測試全部仍通過。
- 完整測試 `.venv/bin/python -m pytest -q` 全部通過。
- 不安裝、不載入任何 launchd 工作；不修改 `config/submit_mode.json`、`config/tournaments.json` 與送出白名單；不修改 `src/submit.py`。

### 與規格不同之處及理由

- **M3-W1 撤銷介面尚待整合**：本 clone 尚無 `src/submit.py`，僅能依任務指定的 `run` CLI 契約實作與測試呼叫。若舊整合已發布為 `submission_eligible=true`、尚未建立送出意圖，而下一輪因修訂作廢，現有 `run` 契約無法指定逐筆排除；本版追加作廢事件並保守阻擋整批送出，記為 `obsolete_submission_eligible_aggregate`。其他研究仍繼續，但這比規格只阻擋受影響題目更嚴格。須由後續 M3-W1 整合追加撤銷事件的讀取契約才能解除；不得刪除歷史或把舊答案改掛新快照。此限制代表本工作尚不能作為 trial 上線驗收的完整證據。
- 預算採明確、最多七天且不可重疊的窗口；不自動展延，也不替未量測的正式額度填預設上限。到期後拒絕新週期的模型工作，下一窗口須事先設定。這是沿用既有 `budget.py` 需要明確窗口／上限的保守選擇。
- 不以字詞相似度猜測「實質」修訂；輪詢已產生的新內容快照一律視為修訂。題型、選項、截止時間及 post／tournament 對應改變均禁止舊結果回退；其餘文字變更才可回退。
- 除週期內的准入與單次 CLI timeout 外，增加 supervisor：600 秒週期間隔、30 秒安全餘裕、最後 60 秒留給刷新與送出，第 560 秒開始預留 10 秒清理程序。持續模式的第 1 層 timeout 可縮到週期截止；第 2 層仍須容納既有 p90／未量測保守估計，否則留待下一輪，決策截止時採用合格第 1 層。`/bin/ps` 無法確認後代清理時明確記錄 `cleanup_unverified`，不宣稱已驗證程序全部退出。

### 第 1 輪修正

本節更新第一版執行回報中已被審查推翻的設計與限制；上方第一版回報保留作歷史紀錄。本輪未修改規格、驗收條件或審查紀錄。

- **B1（已處理）**：`execution_deadline` 現在只限制 scheduler 接新工作與每次嘗試前的 `recheck`；移除 `Context` 的週期截止欄位及 `run_attempt` 對 `decide_by` 的週期截斷，已開始的呼叫保留正常各層 timeout，仍受該題決策截止點約束。移除第 1 層 `MIN_ATTEMPT_S + 60` 與第 2 層須在週期內完成的額外條件，沿用 M2 的預算／題目截止准入。預設准入窗口仍為 510 秒；截止後等現有工作結束，再刷新、finalize、publish、submit，全程保有 `cycle.lock`。`submit.py run` 固定 120 秒 timeout。
- **B1 的 supervisor**：完整嘗試鏈為 initial → format_repair → rerun → format_repair，每次 Gemini 嘗試含前後各一次額度查詢。單一工作上界 `2 × (max(tier1, tier2) + repair + 4 × QUOTA_QUERY_S)`；三線平行，取最長單線。硬上限為「准入窗口 + 單一工作上界 + 120 秒送出 + 10 秒清理」。現行設定得到 3240 秒單一工作、3870 秒 worker、3880 秒含清理硬上限。正常與 supervisor 補記的 `cycles.jsonl` 都包含 `admission_deadline` 與 `timing_limits`；parent 將開始時間及准入截止傳給 worker。`launchd/README.md` 已同步說明。
- **B1 的接續補充（審查未逐項指定，採保守作法）**：第 2 層因週期截止而 `stopped_waiting` 時，不再轉成永久 `not_admitted`，保留下一輪重跑機會。若截止恰在主嘗試與格式修復之間，持續模式將原始修復文字與既有 `repair_basis` 追加保存在嘗試紀錄，下一輪只接續該次尚未開始的修復，不增加 initial／rerun 次數，也不重新採樣答案；仍走既有稽核、預算、輸入重查與未知 start 阻擋。固定 M2 模式不使用這項接續。理由是單純停止准入會讓已完成主嘗試的待修復工作被誤判為 `attempts_exhausted`。
- **B2（已處理）**：移除 `publish()` 發現過期已發布結果時的提早返回。已作廢快照仍禁止新發布；過期 ID 只放在 `stale_aggregate_ids`，新快照及其他題可正常發布並呼叫 submit。採用審查指定的 M3-W1 契約：送出端拒絕快照 ID 出現在 `question_queue.jsonl` 的 `snapshot_invalidated.old_snapshot_id` 中的整合與意圖。本 clone 無 `src/submit.py`，未修改或建立送出端，實際拒絕行為須在合併後驗收；這是驗證範圍限制，沒有改用其他契約。
- **B3（已處理）**：只以 `status="intent"` 且相同 `intent_id` 沒有 `abandoned` 的意圖判定 committed；不再用 `state`／`type` 或其他狀態猜測。沒有 intent 的 `dry_run`、`rejected_precheck`、成功／未知狀態均不凍結題目。以 intent ID 逐筆解除，同題還有其他未放棄意圖時仍凍結。另處理已觀測新快照並記成 `already_submitted` 後才 abandoned 的情況：恢復先前快照綁定，以便正確追加舊快照作廢及重排；不要求再出現一次修訂。快照未變時不把自身作廢，不重跑已完成答案。理由是僅修改 committed 集合仍可能留下不可恢復的佇列狀態。
