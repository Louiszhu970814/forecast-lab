# M3-W8 trial 前的送出與持續週期契約修正

狀態：規格（Claude，2026-11-01）。實作：GPT。審查：Claude。

依據：`docs/tasks/AUDIT-ARGON-2026-11-01.md`（Gemini 稽核，Claude 已核對）。本任務只處理會讓 trial 送錯、漏送或安全檢查失效的問題。題集的每週滾動（稽核 B4）需要 Louis 先決定上限政策，另立任務，不在本任務範圍。

## 問題（已由 Claude 核對屬實）

1. **送出端只讀靜態場地設定**（稽核 B1）：`Submitter._policy()` 只用 `load_tournaments()`。
   - `_gate()` 要求 `intent["tournament_id"]` 唯一出現在靜態清單；但 Metaculus Cup 與主站題目的 ID 是執行時才由 `m2_campaign.discover_tournaments()` 發現的，不在 `config/tournaments.json`。
   - `_precheck()` 要求 `minibench.id` 為正整數；實際設定是 `null`（MiniBench 每輪換 ID，PLAN §9 規定必須涵蓋所有 ongoing／upcoming 輪次）。
   - 結果：在真實設定下切到 `trial`，所有送出都會變成 `rejected_precheck`。既有測試把 `minibench.id` 改成假整數，所以沒有抓到。
2. **送出全部被拒絕時，週期仍記為 ok**（稽核 B2 的觀測部分）：`submit.py main()` 除了 busy 以外一律回傳 0，`cycle.submit_cli()` 只看 returncode，`cycles.jsonl` 會寫 `submit: ok`。
3. **持續模式的排程器閒置就結束，可能錯過送出窗口**（稽核 B3）：`Scheduler.run()` 在 `if not active: break` 結束。某條線暫停時，題目要到決策截止點（`close − 25 分鐘`）才封存；送出截止是 `close − 20 分鐘`，而 launchd 每 600 秒才啟動一次週期。決策截止點那一刻可能沒有任何週期在執行。
4. **暫停的線讓第 2 層整體停擺**：`Scheduler.jobs()` 的 `unfinished_first` 把暫停、等待額度、被 preflight 擋下或停線的線也算成「第 1 層未完成」，所以只要一條線暫停，所有題目的第 2 層都不會開始（今天 M2 實測時，gemini 停在保留線就是這樣）。
5. **Gemini 週額度保留線觸發時記為停線**：`forecast.gemini_admission()` 的週額度不足會丟出沒有 `quota_retry_at_utc` 的 `LineStop`，結果記為 `line_stopped`。M2-W9 已把 5 小時額度不足改成 `quota_5h_wait`，週額度不足也應該是可等待的狀態，而不是停線。
6. **第 1 層的正式驗收紀錄沒有核對版本與程式碼**（稽核 B5(3)）：`forecast.check_acceptance()` 只對第 2 層的正式驗收紀錄核對 `cli_version`、`judge_version` 與 `code_sha256`。第 1 層可能沿用舊 CLI 或舊程式碼下的正式驗收。

## 需求

1. **送出端的場地身分**（`src/submit.py`）：
   - `Transport` 增加取得「目前場地對應」的方法：試驗場地由官方 API 發現（與 `continuous.Poller` 相同的 `discover_tournaments()` 邏輯，不修改 `config/tournaments.json`），並列出所有 ongoing／upcoming 的 MiniBench 輪次。
   - `trial`：`intent["tournament_id"]` 必須唯一對應到一個試驗場地類型（`trial_ground_types`），而且不是主賽或任何 MiniBench 輪次。排除索引必須涵蓋主賽與所有 ongoing／upcoming MiniBench 輪次；只要有一輪不在 `index.project_ids`，就拒絕（暫時性，可重試）。`minibench.id` 為 `null` 是合法設定。
   - `live`：維持現有的靜態白名單規則（`submit_whitelisted` 為真、ID 為整數）。不得因本修改放寬 `live`。
   - 發現失敗、結果不完整或前後不一致時，一律拒絕（暫時性），不得改用靜態設定替代。
   - 新增使用**真實形狀**設定的測試：直接讀 repo 內的 `config/tournaments.json`（`minibench.id = null`，不含 Cup／主站的靜態條目），搭配假 Transport 回傳的發現結果。至少涵蓋：bot testing area、Cup、主站題目在 trial 都能通過；主賽、任一 MiniBench 輪次、未知 ID 都被拒絕；漏掉一輪 MiniBench 的排除索引被拒絕。
2. **送出結果的觀測**：
   - `submit.py run` 的 stdout 改為單行 JSON（目前是 Python dict 的 repr），只含計數，不含題目資訊。
   - `cycle.submit_cli()` 解析這個 JSON。這次執行新增的事件只要有 `rejected_precheck`、`unknown`、`confirmed_failed`、`forecast_failed`、`comment_failed` 或 `abandoned`，`status` 就是 `attention`，並附上各狀態的計數；只有沒有這些狀態時才是 `ok`。解析失敗記為 `error`。
   - `ops_report`（Telegram 報告）把 `attention` 視為需要注意的週期狀態（它目前只認得固定的狀態集合）。
3. **持續模式的決策截止點必須有程序在執行**（`src/scheduler.py`、`src/cycle.py`）：
   - 不變量：在 launchd 每 600 秒啟動一次週期的前提下，對每一個未封存的題目，它的決策截止點之後 60 秒內，必須有一個週期程序執行 `finalize()`。
   - 建議作法：持續模式下沒有工作在跑時，如果最早的未封存決策截止點落在「現在 + 下一次週期一定已經啟動的時間」以內，就等到那個時間點再 finalize，而不是直接結束；同時遵守週期監督者的總時間上限（`cycle.timing_limits()`）。如果上限不夠，要在接近上限時讓下一個週期接手，不能留下空窗。GPT 可以提出更簡單、同樣能證明不變量的作法，並在執行回報說明。
   - 等待期間不得忙迴圈；`STOP_SUBMIT` 存在時照現有規則不送出。
   - 加入整合測試：某條線暫停、其他線早早完成第 1 層、之後一段時間完全沒有工作，題目仍在決策截止點後 60 秒內封存並送出。這個測試**不得**靠另一題的長工作來維持排程器存活（現有的 `tests/test_m3_integration.py` 就是這樣，所以沒抓到）。
   - 同步更新 `coverage_sim.py`，讓模擬器也反映新的結束與等待規則，並新增對應的模擬案例；更新 `docs/coverage_sim.md` 的差異清單。
4. **暫停的線不阻擋其他線的第 2 層**（`src/scheduler.py`）：
   - 只在**持續模式**修改；固定 M2 題集的行為不變，因為進行中的 M2 題集仍在使用。
   - `unfinished_first` 只計算本輪實際能執行的第 1 層工作：線已啟用，而且不在 `paused`、額度等待、preflight 擋下或停線狀態。
   - 第 1 層仍然優先（D52）：只要還有能執行的第 1 層工作，就先做第 1 層。
   - 題目的升級判斷（`E.evaluate`）只用已完成的第 1 層結果，照現有規則處理缺線；缺線的線之後恢復時，照常補做它的第 1 層。
5. **週額度保留線改為等待**（`src/forecast.py`、`src/scheduler.py`、`src/reconcile.py`）：
   - `gemini_admission()` 週額度不足時，丟出帶有 `quota_retry_at_utc`（週額度桶的 `reset_time`）的 `LineStop`，結果記為 `quota_weekly_wait`。排程器對它的處理與 `quota_5h_wait` 相同。
   - 它不是安全停線，不通知 Louis，也不寫 `line_stop`。
6. **第 1 層正式驗收的新鮮度**（`src/forecast.py`）：
   - `check_acceptance()` 對第 1 層的正式驗收紀錄，也要核對 `cli_version`、`judge_version` 與 `code_sha256`，規則與第 2 層相同。
   - 不改「最新一筆驗收必須通過」的規則：任何一層的驗收失敗，兩層都停。這是保守設計，維持不變。
