## 問題

`cycle_v2` 要等 `scheduler.run()` 結束，也就是等所有執行中的工作都結束，才 publish 與 submit。執行中的工作最長可達第 2 層 1200 秒，再加上格式修復，因此已封存的題目可能因為別題的長工作而錯過送出截止（關閉 − 20 分鐘）。這不符合 §3.5「到了決策截止點，所有等待中的工作都停止等待，依 §3.4 第 9 點送出已有的合格結果」。M3-W3 審查時，模擬器差異清單第 8 項揭露了這個問題。

原因有兩個：

- `submit.py` 與排程器共用 `scheduler.lock`，而且在整個 `run()` 期間（包括傳輸層呼叫與留言退避）都持有帳冊交易，所以排程器執行時不可能送出。
- 排程器主迴圈以 `wait(..., FIRST_COMPLETED)` 等待，在沒有工作完成之前不會醒來，到了決策截止點也不會 finalize。

## 規格（協調者的設計決定）

1. **送出端的鎖**（修改 `submit.py`，升版）：
   - 改用專屬的非等待鎖 `data/submit.lock`，不再使用 `scheduler.lock`。另一個送出程序正在執行時直接結束並回報忙碌，不排隊。
   - 帳冊交易只包住讀取與追加的步驟，不得在傳輸層呼叫、讀回或退避等待期間持有。每次寫入前仍要重讀帳冊，判斷該意圖的最新狀態；兩個送出程序不可能同時執行，因為有 `submit.lock`。
   - 其他送出前檢查、狀態機與停用開關都不變。
2. **排程器在執行中觸發送出**（修改 `scheduler.py`，升版）：
   - 新增可選的 hook，例如 `on_finalized(newly_ready_question_ids)`，只在持續模式下使用。主迴圈每次 finalize 後，若有題目新完成可送出的最終整合，就呼叫它。
   - 主迴圈的等待要設 timeout：最晚在「尚未封存的題目中最早的決策截止點」醒來，至少每 60 秒醒來一次。醒來後 finalize，讓到了決策截止點的題目依 §3.4 第 9 點封存。固定 M2 題集的行為不變。
3. **週期在排程中送出**（修改 `cycle.py`，升版）：
   - hook 的內容是 publish（現有的 `publish()`，需要時取得帳冊交易），接著以子程序執行 `submit.py run`，timeout 維持 120 秒。若送出程序因 `submit.lock` 忙碌而跳過，記錄後繼續。
   - hook 在排程器主執行緒中同步執行；執行期間排程器不接新工作，但已在執行的工作不受影響。每次呼叫都要記入 `cycles.jsonl` 的步驟結果（呼叫次數、每次的結果與耗時）。
   - 週期結束時的 publish 與 submit 保留。
   - `STOP_SUBMIT` 存在時，hook 不呼叫 submit（與現行週期結尾的行為一致）。
4. **模擬器同步**（修改 `coverage_sim.py`，升版）：依新的週期行為模擬「排程中送出」，以及送出程序忙碌時跳過；更新 `docs/coverage_sim.md` 的差異清單。可以保留舊行為作為可選的政策，供比較。

## 驗收條件

- 測試（假時鐘、假 adapter、假傳輸層）涵蓋：
  - A 題的長工作執行中，B 題到了決策截止點，在 B 題的送出截止前就完成 publish 與送出；A 題的工作不受影響。
  - 沒有任何工作完成時，排程器也會在決策截止點醒來並封存題目。
  - 送出程序執行中，排程器的帳冊寫入不會被傳輸層呼叫阻塞，例如假傳輸層在呼叫期間由另一個執行緒寫入帳冊，必須立刻成功。
  - 兩個送出程序同時啟動時，第二個回報忙碌且不寫入任何紀錄。
  - 送出時中斷、重啟後的對帳行為與 `submit_v3` 相同（既有測試仍通過）。
  - `STOP_SUBMIT` 存在時，排程中不送出。
  - 模擬器：在相同的合成時間表下，新行為的準時覆蓋率不低於舊行為；並有一個案例是舊行為漏答、新行為準時送出。
- `tests/test_m3_integration.py` 全部通過，並新增一項「排程中送出」的整合情境。
- 修改既有測試的預期時（例如原本驗證送出端與排程器共用鎖的測試），在回報中逐項說明理由。
- 完整測試 `.venv/bin/python -m pytest -q` 全部通過（沙箱中因 `TMPDIR` 位於 clone 內而失敗的既有隔離測試，列出名稱即可，不要修改）。
- 不連網、不呼叫模型 CLI、不安裝 launchd、不修改正式設定。

### 與規格不同之處、假設與保守決定

- 沒有調整任務規格或驗收條件。忙碌的 Python 回傳及 CLI 退出碼原規格未指定，採 `busy`／75，cycle 將其記為忙碌後繼續，不把它當成整輪錯誤；忙碌者不讀寫送出帳冊。
- hook 只在 ready final 及其留言成功建立時通知；重啟後補建遺失留言也會通知，無合格答案或留言建立失敗不通知。此處的「可送出」仍由既有 publish／Submitter 的模式、身分、白名單、作廢、稽核與截止檢查最終裁決，沒有直接把 local final 改成 eligible。
- hook 忙碌、傳輸子程序逾時或其他例外均保留逐次結果；例外只記類別，不記可能含敏感內容的文字，排程繼續，週期結尾仍可對帳／補送。每次仍為 120 秒 timeout；既有 supervisor 硬上限未放寬，多次同步 hook 也計入該上限。
- STOP 存在時，hook 沿用原週期結尾的選擇，同時略過 publish 與 submit，但記錄此次 hook 的停止原因；研究繼續。每次真正寫入 API 前仍由 Submitter 重查開關。
- 解除長交易後，遠端前檢期間可能新增作廢或稽核事件，因此在 `request_started` 前的短交易再次驗證凍結輸入、去重、開關與本地截止，才記錄請求開始。遠端呼叫仍在交易外；不增加新重試路徑、不改對帳證據要求。
- 持續模式喚醒時沿用 Queue 的快取刷新，故可能比舊版提早看見新題；同步 hook 期間不接新工作，既有工作不被取消。文字修訂 fallback 仍沿用原 Queue 的排除與週期結尾 force finalize，不另改修訂政策；模擬器同步這個邊界。
- 模擬器的 `submission_policy` 預設 `on_finalized`，忙碌區間預設空清單；選 `cycle_end` 時也保留舊版沒有計時喚醒的等待政策。忙碌區間只表示外部持鎖，不假設外部程序已替任何題目送出。v1 凍結紀錄不能冒用 v2 引擎，需以新 ID 重新登記。
- 三組相同合成時間表中新政策的準時覆蓋率均不低於舊政策，其中雙題案例舊政策第一題因別題的 1200 秒工作而晚送，新政策準時送出。這是合成案例驗證，不是所有負載下的單調性保證；同步送出、輪詢與 supervisor 仍可能造成延遲。模型輸出、HTTP／留言內容及外部持鎖者的工作仍採文件所列抽象。
- 依 AGENTS.md 及 M3-W2 審查 N1，PLAN 正文、文件版本與 §16 留由協調者整合；本回報保存待整合版本紀錄：`submit_v4`／`scheduler_v4`／`cycle_v3`／`coverage_sim_v2` 將持續模式由排程結束送出改為封存即送出，固定 M2 模式維持原行為。未修改 prompt、模型參數、篩題設定、正式送出模式或白名單。
