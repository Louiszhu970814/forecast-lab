## 為什麼需要

試驗期只在試驗場地作答，主賽與 MiniBench 只抓中繼資料。正式參賽前，要用實測的耗時重播主賽與 MiniBench 的實際開題時間，估計在 §9 的並行度與 `cycle_v2` 的週期設計下，能準時完成多少題。M3-W2 的審查也留下兩個要量測的取捨：一個週期最長約 65 分鐘，期間出現的新題要等下一輪；任何內容修訂都會重跑三線第 1 層。

## 本工作的範圍

只做模擬器與它的測試，使用合成的題目時間表與耗時分布。真實資料（主賽與 MiniBench 的開題、關閉時間；M2 的實測耗時、升級率與格式修復率）由協調者之後收集，再用本工具執行；不在本工作中連網或讀取真實帳冊。

## 規格

1. **`src/coverage_sim.py`**：離散事件模擬，以虛擬時鐘執行，不呼叫模型、不連網、不寫正式帳冊。
2. **輸入：一份模擬設定（JSON），執行前先登記並凍結**（D53：「觀察期間與分母在看結果前固定」）：
   - 觀察期間（UTC 起訖）與分母的定義：哪些場地、哪些題目；以 `open_time` 落在觀察期間內為準。
   - 題目時間表檔案：每題的 `question_id`、場地（`main`／`minibench`）、題型、`open_time`、`scheduled_close_time`，以及可選的修訂事件（時間、是否為結構修訂）。
   - 各線、各層的耗時分布（實測樣本清單或參數），格式修復率與耗時、第 1 層失敗後重跑的比率、升級到第 2 層的比率；額度重置時間與停線區間（例如 `quota_exhausted`、單線停用）。
   - 隨機種子與重複次數。
   - 登記方式比照 `continuous.register`：追加到 `data/coverage_sims.jsonl`，紀錄設定的 sha256 與內容；同一 ID 的設定不能改變。執行時核對 hash。
3. **要模擬的行為**（盡量重用既有函式，例如 `forecast.decision_deadline`、`validate.submit_deadline`、`budget.duration_estimate` 與排程器的優先序；無法直接重用的部分，在模擬器中實作並在回報中逐項列出與正式程式的差異）：
   - 每 10 分鐘一個週期；週期的准入窗口、執行中工作不被截斷、`overlap_skipped`、supervisor 上限都依 `cycle_v2`。
   - 新題只在週期內的輪詢（含每完成一個工作後的刷新）被看見。
   - §9 的並行度（三線平行、每線同時 1 個工作）與優先序（主賽第 1 層 > MiniBench 第 1 層 > 主賽第 2 層 > MiniBench 第 2 層；MiniBench 即將截止的例外）。
   - §3.5 的截止：送出截止 = 關閉 − 20 分鐘；決策截止 = 送出截止 − 5 分鐘；第 2 層只在 p90 預估完成時間早於決策截止時才啟動。
   - §7.5：首次嘗試、格式修復、一次重跑。
   - 修訂：來得及就以新快照重跑三線第 1 層；來不及時依 D53 處理。
   - 送出所需時間（留言、送出前檢查與送出）。
4. **輸出**（追加到 `data/coverage_sim_results.jsonl`，並可輸出摘要）：
   - 全部題目的覆蓋率，以及已支援題型的準時覆蓋率；90% 的門檻只適用於已支援題型，`unsupported_type` 仍列在全體分母中。
   - 每題的結果：準時送出（含第 2 層與否）、漏答原因（`timeout`、`quota_exhausted`、`unsupported_type`、`budget_skipped`、`late` 等）。
   - 各線的使用率、佇列等待時間的分布、同時開題的高峰、週期超過 600 秒的比例，以及新題從開題到開始第 1 層的延遲分布。
   - 重複次數大於 1 時，報告平均值與分位數。
5. **CLI**：`python src/coverage_sim.py register <設定>`、`python src/coverage_sim.py run <設定 ID>`。

## 驗收條件

- 單元測試（合成時間表、固定種子）涵蓋：單題在空佇列下準時完成；同時開題超過並行度時的排隊與漏答；第 2 層因預估時間不足而不啟動；週期超過 600 秒時新題延到下一個週期；格式修復與重跑；修訂來得及與來不及兩種情形；停線區間造成的漏答與原因；`unsupported_type` 計入全體分母但不計入已支援題型的分母；凍結設定的 hash 核對與不可變更；相同種子結果相同。
- 至少一項測試，比較模擬器與 `scheduler.jobs()` 在相同狀態下選出的下一批工作，確認優先序一致。
- 完整測試 `.venv/bin/python -m pytest -q` 全部通過（沙箱中因 `TMPDIR` 位於 clone 內而失敗的既有隔離測試，列出名稱即可，不要修改）。
- 不連網、不呼叫模型 CLI、不讀取 `data/` 下的真實帳冊、不修改正式設定。

### 與正式程式的差異（逐項）

1. 不執行正式 `Scheduler.run()`／`Queue`／`Budget.reserve()`，以記憶體狀態與虛擬工作槽重建流程，避免正式帳冊、外部呼叫與 wall-clock 等待。直接重用 `decision_deadline`、`submit_deadline`、`duration_estimate`、`quantile`、`Job/order_jobs`、`cycle.timing_limits`。
2. 以登記的時間表代替 API 輪詢；週期從觀察起點每 600 秒啟動。強制完成後刷新及呼叫前的 30 秒快取重查保留，但初始化／preflight／查詢延遲分別用固定 `startup_s`／`poll_s` 表示，不檢查真實 baseline 或帳號。
3. 只模擬分母選中的題集，期初佇列與被排除題目的競爭負載為零；真實評估須納入完整的主賽／MiniBench 負載並選足夠早的起點。觀察期間結束後繼續處理至最後一題關閉，避免期末開題被截斷。
4. 耗時採經驗樣本有放回抽樣；格式修復、首次非格式失敗、重跑失敗、修復失敗與升級以明列機率抽樣。沒有機率答案、JSON Schema 內容、來源稽核或分歧公式；不模擬跨線相關性。每快照最多 initial／rerun 各一次、各自最多一次 repair，並保留跨週期待修復狀態。
5. p90 以登記樣本初始化，再加入模擬耗時並沿用正式最近 50 筆算法與固定餘裕。實際嘗試額外預留整份 `overhead_s`，不細分 Gemini 的前後 quota 查詢；歷史模擬耗時含 overhead，再加估時餘裕可能偏保守。
6. 預算以每線明列的 attempt cap、預期新題／修復保留與 reset 時間表示，兩層、修復、重跑均消耗次數。不推估 Argon 百分比、token 熔斷、個人保留線或先前驗收用量；請由協調者把可用容量及停線區間預先轉入設定。`budget_skipped` 為該快照／線／層終局，reset 釋放新題容量，不重新選答。
7. 修訂輸入只提供時間與 structural 標記，不重建題文／選項／對應或修訂後的新截止時間。刷新才發現修訂；來得及就重跑三線，來不及則結構修訂阻擋、文字保留舊快照。已執行的舊快照工作繼續占用線，但結果不採用；已送出只記修訂。
8. 以至少一條有效線表示可整合，保留缺線與第 2 層失敗回退；不計算正式機率與留言內容。沿用整個週期排程結束才發布的行為，沒有另建決策截止送出執行緒，因此會呈現其他長工作造成的晚送風險。
9. 留言／前檢／送出以每題固定秒數合計，依題號串行處理，共用正式 120 秒上限；未開始者延後、執行中逾時者保守記 timeout／結果未知，不算覆蓋。不模擬 HTTP、遠端重試、讀回、留言單獨補送與身分／白名單驗證。送出階段會檢查該題新修訂，不藉此提前發現別的新題。
10. supervisor 沿用 worker 上限及獨立 cleanup reserve，以虛擬截斷取代程序樹終止；被截斷工作保守作終局失敗，不模擬未完成帳冊的人工恢復。同時事件採固定線順序、完成先於鎖判定，結果可重現。明列停線不截斷已啟動的呼叫，後續呼叫重查；週期開始已停線則該輪保持暫停。

### 與規格不同之處及理由

- 規格與驗收條件原文未修改。使用規格允許的「實測樣本清單」介面，未另外提供參數式分布；可藉重複樣本表示權重。
- 額外凍結時間表內容與引擎時間政策，而非只保存檔名；避免原檔修改、deadline 或 timeout 改變後仍冒用舊 ID 的結果。`run` 不再讀原設定／時間表檔。
- 增加獨立使用說明文件、`--data-dir`、逐嘗試／輪詢／週期明細與多因診斷欄位，讓協調者可重播、追查與審查。
- 上述正式程式差異都是離線抽象；沒有改動正式預測行為、prompt、模型參數、篩題政策或設定，因此沒有修改 PLAN 正文／版本號／§16。工作目錄原有的 `docs/tasks/M3.md` 變更保留未動。

### 假設與指標解讀

- 分母固定為半開區間 `start <= open_time < end`，再與場地及明列 ID 取交集；支援題型固定 binary／multiple_choice。空分母回報 null，不視為達成 90%；unsupported_type 留在全體分母。
- seed 加重複次序形成每次獨立亂數源；相同凍結內容及 seed 可重現完整結果。JSONL 寫入的實際 UTC 時間不屬於亂數結果。
- 截止採現行設定（close − 20 分鐘、再減 5 分鐘），第 2 層估時須嚴格早於決策截止；三線各最多一個工作。正式策略的全域「未完成第 1 層就不啟動第 2 層」也適用忙碌與 quota 停線。
- 使用率分母只取觀察期間，尾段工作仍決定逐題覆蓋；週期超過 600 秒的比例含模擬尾段的實際啟動週期、不含 overlap_skipped。等待／開題延遲只統計真正開始者，另列 not_started，避免把漏答當零延遲。
- 漏答可同時有多個原因，保留 contributing_reasons；主因依明確修訂／送出錯誤，再依 quota、disabled、preflight、budget、timeout、輸出失敗排序，是診斷標籤而非因果判定。分位數為最近秩法；跨次分位數不是統計信賴區間。
- 假設時間表對每個 question ID 唯一，修訂已預分類；所有不確定遠端送出均不算成功。無真實量測結果，不能據此宣稱 90% 覆蓋或核准參賽。
