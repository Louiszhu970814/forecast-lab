# M1-W7：Metaculus 唯讀 client 與 `poll_questions.py`

> 執行：Claude｜審查：Gemini｜依賴：W1
> 對應 PLAN：§3.1（試驗場地）、§3.2（題目取得、題目修訂）、§3.3（不抓社群預測）、§3.6（post ID 與 question ID）、D45、D46、D50、D52、D53；使用條款（不爬取頁面、不儲存大量內容）。

## 交付物

- `src/metaculus.py`：唯讀 API client，只發 GET 請求。
- `src/poll_questions.py`：查詢場地中開放的題目，依白名單欄位建立快照，寫入 `data/questions.jsonl` 與 `data/poll_log.jsonl`。
- `tests/test_poll_questions.py`：使用合成的題目資料，不含真實題目內容。

## 執行回報

執行者：Claude（2026-10-31）。

- client：
  - 以 `Authorization: Token` 驗證；token 不出現在 `repr`、例外訊息或紀錄中。
  - 429 與 5xx 依 `Retry-After` 或指數退避重試。
  - 只追蹤同一個 API 主機的 `next` 連結。
  - 實測發現 API 在最後一筆之後仍會一直回傳 `next`，所以遇到空頁就停止；另設最多 20 頁的上限。
  - 沒有任何送出預測或留言的函式，那屬於 M3 的 `submit.py`。
- 場地必須以數字 ID 指定：實測中，以代號（slug）查詢時 API 會忽略篩選並回傳全站題目，上限阻止了大量抓取。`resolve_venue` 從 `config/tournaments.json` 對應 ID，找不到就拒絕執行。
- 快照只保存白名單欄位：
  - 識別：`post_id`、`question_id`、`project_ids`；
  - 內容：`question_type`、`title`、`description`、`resolution_criteria`、`fine_print`、`options`；
  - 時間：`open_time`、`scheduled_close_time`、`scheduled_resolve_time`。

  `aggregations`（社群預測）、`cp_reveal_time` 與 `nr_forecasters` 不保存（D50）。
- 題目修訂（D52）：內容 hash 或關閉時間改變時，追加一筆新快照，並以 `revision_of` 指向前一筆，`t0` 沿用第一次看到的時間。
- 同步題排除（D53）：題目屬於白名單比賽的 project，或標題與開放中的比賽題目相同時排除。後者只算疑似，判斷以 ID 為主。
- `--metadata-only`：試驗期對主賽與 MiniBench 只記錄時間與題型，不寫入快照（D45）。
- 實測（2026-10-31）：
  - bot testing area 有 7 題，其中支援的是非題與多選題共 3 題；第二次查詢正確判為未改變。
  - 2026 秋季主賽當時沒有開放中的題目。
- 測試：全部 127 個測試通過。

尚未處理：

- MiniBench 的數字 ID 還沒查到，`config/tournaments.json` 中為 `null`，`resolve_venue` 會拒絕。
- 同步題排除需要「開放中的比賽題目」清單作為輸入，主流程（W8）要先以 `--metadata-only` 查詢比賽，再傳入排除條件。

## 審查紀錄

審查者：Gemini（2026-10-31）

各項審查重點核對結果：
1. **唯讀與安全**：`MetaculusClient` 只發送 `GET` 請求；`__repr__` 與 `MetaculusError`（含 `raise ... from None`）均未暴露 token；分頁強制檢查 `https` 與同主機（`_host`），遇空 `results` 即停止並有 `max_pages=20` 上限；429/5xx 支援 `Retry-After` 與指數退避（上限 60 秒）。
2. **白名單欄位與社群預測排除**：`snapshot_from_post` 以白名單鍵重建 dict，`aggregations`、`cp_reveal_time`、`nr_forecasters` 等聚合與社群預測欄位均在寫入前排除（符合 D50）。
3. **題目修訂、同步題排除與 metadata-only**：`record_snapshots` 比對 `content_hash` 與 `scheduled_close_time`，變更時追加新快照、保留原 `t0` 並設定 `revision_of`（符合 D52）；`--metadata-only` 不寫入 `questions.jsonl`（符合 D45）。
4. **使用條款**：全程只呼叫官方 REST API，不抓取網頁 HTML，不儲存非必要欄位。

審查意見：

- [src/poll_questions.py、src/metaculus.py] `resolve_venue` 目前只在 `main()` 呼叫，而 `poll()` 與 `MetaculusClient.list_posts()` 直接接受任意 `str` 並傳入 `tournaments` 參數（`tests/test_poll_questions.py` 也直接傳 slug 給 `poll()`）；此外 `main()` 將 `str(resolve_venue(args.venue))` 作為 `venue` 傳入 `poll()`，使寫入快照與 `poll_log` 的 `venue` 變成數字字串（如 `"32977"`）而非場地代號，且快照缺少明確的數字 `tournament_id` 欄位（`PLAN.md` §3.2、D46）。建議：在 `poll()` 內呼叫 `resolve_venue(venue)` 取得數字 `tournament_id`，並在 `list_posts()` 驗證 `tournament` 為整數（或數字字串），同時於快照與 `poll_log` 分別記錄 `venue`（slug）與 `tournament_id`（int）｜實測已知 Metaculus API 收到非數字 slug 時會忽略篩選並回傳全站題目；若 W8 主流程比照測試直接以 slug 呼叫 `poll()`，會繞過 `resolve_venue()` 並抓回大量全站題目（最多 20 頁共 1,000 題），既有違反使用條款「不儲存大量內容」的風險，也會汙染 `questions.jsonl`｜non-blocking
- [src/poll_questions.py] `--metadata-only` 模式的 `timing` 只記錄 `question_id`、`question_type` 與三個時間欄位，未包含 `post_id` 與標題（或正規化標題 hash），且 `is_synced_copy()` 只檢查 `tournament_project_ids` 與 `tournament_titles`（未檢查 `question_id` / `post_id`，也未對傳入的 `tournament_titles` 做 `.strip().lower()` 正規化）；另外查詢比賽時預設只查 `statuses="open"`，未涵蓋即將開放（`upcoming`）的題目。建議：(1) `is_synced_copy()` 補上 `question_id` / `post_id` 比對，並在函式內將 `tournament_titles` 正規化為 `.strip().lower()`；(2) `--metadata-only` 的輸出補上 `post_id` 與標題雜湊（或正規化標題），並在查詢比賽中繼資料時涵蓋即將開放題目，讓 W8 主流程能直接以 `--metadata-only` 的結果作為同步題排除輸入｜`PLAN.md` §3.1（D53）規定試驗場地須排除與主賽或 MiniBench「開放中、即將開放」相同的題目，且「判斷以平台的 ID 與歸屬對應為主；標題相同只當作疑似重複的訊號」；目前 `--metadata-only` 的輸出還不足以讓 W8 單靠該紀錄完成 ID 與標題排除｜non-blocking
- [src/poll_questions.py] `record_snapshots()` 在偵測到題目修訂時，`rec["revision"]` 目前只記錄 `content_changed` 與 `close_time_changed`。建議一併記錄 `type_changed`（`prev.get("question_type") != snap.get("question_type")`）與 `options_changed`（`prev.get("options") != snap.get("options")`）｜`PLAN.md` §3.2（D53）規定題目修訂來不及重跑時，須區分「題型、選項或截止時間改變（不送出）」與「只有文字修訂（送出舊快照結果）」，在修訂欄位直接標示可減少下游重複比對前後快照的負擔｜non-blocking
- [tests/test_poll_questions.py] 現有測試已涵蓋核心防護與快照邏輯，建議在修正上述項目時一併補上：`poll()` / `list_posts()` 拒絕未知非數字 slug 的測試、`is_synced_copy()` 對大小寫標題與 `question_id` 比對的測試，以及 `Retry-After` 與 `max_pages` 超限的單元測試｜確保數字 ID 強制檢查與同步題排除在單元測試層有完整回歸保護｜non-blocking

結論：修改後通過

協調者修正紀錄（Claude，2026-10-31）：審查意見 4 項都已採納。

1. `poll()` 內部呼叫 `resolve_venue()` 取得數字 ID；`list_posts()` 拒絕非數字的 slug。快照與 `poll_log` 分別記錄 `venue` 與 `tournament_id`。`resolve_venue` 改為丟出 `ValueError`，由 `main()` 轉成錯誤訊息後結束。
2. 新增 `TournamentIndex`：從 `--metadata-only` 的查詢結果建立 question ID、post ID、project ID 與正規化標題 hash 的集合；`is_synced_copy()` 先比對 ID，再比對 project，最後才比對標題（只算疑似）。metadata-only 的 `timing` 加上 `post_id`、`status` 與 `title_key`，並同時查詢 `open` 與 `upcoming`。
3. 題目修訂另外記錄 `type_changed` 與 `options_changed`。
4. 補上測試：slug 被拒絕、`TournamentIndex` 的建立與比對、標題正規化、`Retry-After`、`max_pages` 上限、修訂旗標。另修正到達頁數上限時多抓一頁的問題。

修正後全部 131 個測試通過；實測：秋季主賽目前沒有開放中或即將開放的題目，測試區 7 題，第二次查詢判為未改變，`minibench` 因為沒有數字 ID 而被拒絕。
