# M3-W6：週期與送出的整合測試

- 執行：GPT（代理開發模式，D56）
- 審查：Claude
- 依賴：M3-W1（`submit.py`，`submit_v2`）、M3-W2（`cycle.py`、`continuous.py`，`cycle_v2`／`continuous_v2`）
- 需要閱讀：`docs/tasks/M3-W1.md`、`docs/tasks/M3-W2.md`（兩者的規格、執行回報與審查紀錄）、PLAN §3.2、§3.6

## 為什麼需要

M3-W1 與 M3-W2 是平行開發的。各自的測試都以假的對方代替：`test_cycle.py` 用假的 `submit`，`test_submit.py` 自行寫入整合紀錄與佇列事件。兩者之間的契約從來沒有在同一個流程中實際跑過，包括 `cycle.publish()` 產生的 `submission_eligible = true` 整合結果與留言、`question_queue.jsonl` 的 `snapshot_invalidated`、`submissions.jsonl` 的 `intent`／`abandoned`。

## 目標

新增 `tests/test_m3_integration.py`：以 `cycle.run_cycle` 跑一或多個週期，並把真正的 `submit.Submitter` 接上去，取代假的 `submit`。做法是在測試中以 callable 直接在同一程序內呼叫 `Submitter(root, config_dir=<暫存設定>, transport=<假傳輸層>).run()`。輪詢、adapter、時鐘、傳輸層都使用假的；不連網、不呼叫模型 CLI。

## 情境（每一項至少一個測試）

1. **local 模式**：一個週期完成後，每一筆已發布的整合結果都只產生一筆 `dry_run`；假傳輸層收不到任何呼叫（包括讀取）。原本 `submission_eligible = false` 的 local 最終整合只留下一筆 `rejected_precheck`，第二個週期也不重複寫入。
2. **trial 模式，正常送出**：暫存設定中的 `submit_mode.json` 為 `trial`、`approved_bot_id` 已設定，場地為試驗場地。假傳輸層依序收到預測與留言的寫入，帳冊依序出現 `intent` → `request_started` → `forecast_ok` → `request_started` → `comment_ok`。下一個週期不再送出同一題，佇列也把該題當作已送出。
3. **發布後、建立意圖前修訂**：第一個週期發布後讓 `submit` 不執行或因暫時原因拒絕（例如 `STOP_SUBMIT`），接著題目內容修訂，而且時間來得及重跑。第二個週期作廢舊快照並重排第 1 層；`submit` 不送出舊快照的結果，改送出新快照的結果。
4. **建立意圖後、開始請求前修訂**：意圖已建立，但預測請求尚未開始（例如假傳輸層的帳號讀取暫時失敗）。之後題目修訂，舊意圖記為 `abandoned`，`committed_questions()` 不再凍結該題，新快照可以重新排入並建立新的意圖。
5. **預測已開始、結果未知時修訂**：舊意圖只做對帳，不被 `abandoned`，該題維持凍結，不以新快照重送。
6. **文字修訂來不及重跑**：舊快照的結果在送出紀錄中標記 `text_revised`，且帳冊中有 `revision_fallback = true` 的整合結果；結構修訂（選項或截止時間改變）來不及重跑時不送出。

## 規則

- 整合測試發現兩個模組的契約不一致時，以 PLAN 與兩份任務說明的審查紀錄為準，做最小的修正，並在回報中逐項說明修了什麼、為什麼。修正 `submit.py`、`cycle.py`、`continuous.py` 都可以，但不得放寬任何送出前檢查或停用開關。
- 不修改既有測試的預期，除非它與 PLAN 矛盾；若需要修改，在回報中說明。
- 不修改 `config/` 下的正式設定；測試一律在暫存資料夾建立自己的設定。

## 驗收條件

- 上述六個情境都有測試並通過。
- 完整測試 `.venv/bin/python -m pytest -q` 全部通過；在沙箱中因 `TMPDIR` 位於 clone 內而失敗的既有隔離測試，請列出名稱，不要修改。
- 不連網、不呼叫模型 CLI、不安裝 launchd。

## 執行回報

- 執行者：GPT；2026-11-01；代理開發模式，離線假資料。
- 新增 `tests/test_m3_integration.py`，共 **15 項案例（含參數化）**。每輪由真正的 `cycle.run_cycle` 執行佇列、scheduler、finalize、publish、留言建構，再透過 callable 在同一程序建立真正的 `Submitter(...).run()`；沒有手寫整合結果、送出意圖、放棄意圖或快照作廢事件來替代兩端接線。每輪重新建立 Submitter，以帳冊接續；正常完成也驗證 scheduler 鎖已釋放。

**新增測試與情境對應**：

- 情境 1：`test_local_published_dry_runs_and_local_final_rejections_are_once_only`，兩題各一筆已發布結果只產生一次 `dry_run`；各自的 local final 只拒絕一次；第二輪帳冊不增長，傳輸層連帳號／題目／排除索引讀取都沒有收到。
- 情境 2：`test_trial_publishes_submits_and_freezes_next_cycle`，以 `continuous_v2`／`continuous_v3` 政策各跑一例。驗證完整五步送出狀態、預測 question ID、留言 post ID、機率、留言內容與 hash、私人及附帶預測旗標；第二輪不重跑或重送，佇列為 `already_submitted`。
- 情境 3：`test_revision_after_publication_before_intent_submits_only_new_snapshot`，在 publish 後、呼叫 Submitter 前建立暫存 `STOP_SUBMIT`，實際觸發暫時拒絕。解除後修訂文字，下一輪追加作廢、重排第 1 層並送新快照；舊結果被拒絕，整合歷史的原始位元組前綴保留，後續週期不重送。
- 情境 4：`test_revision_after_intent_before_request_abandons_then_requeues`，文字與截止時間修訂各一例。第一次帳號讀取通過、建立意圖後第二次讀取失敗，因此沒有 `request_started`。修訂後舊意圖只 `abandoned` 一次、解除 committed，下一輪新快照重排並完成送出；同一舊快照只有一筆作廢事件。
- 情境 5：`test_revision_with_unknown_forecast_only_reconciles_and_stays_frozen`，文字／截止修訂 × 讀回空結果／讀回錯誤，共四例。模擬預測已受理但回執遺失；每輪仍對同一 request ID 讀回，相同 unknown 原因不重複入帳；不放棄、不作廢、不重跑、不送新預測。讀回最終成功後只補原留言。
- 情境 6：`test_text_revision_too_late_preserves_old_binding_and_marks_fallback`，先在 STOP 下完成 local final，於距決策截止一分鐘時修訂文字、解除 STOP。發布結果帶 `revision_fallback=true`，預測 `request_started` 帶 `text_revised=true`，兩者仍綁舊快照，不重跑。`test_structural_revision_too_late_rejects_published_result` 另以選項／題型變更及截止時間變更各一例，驗證已發布的舊結果仍被作廢並拒絕，後續週期不產生意圖或傳輸呼叫。
- 額外回歸：`test_revised_offer_rechecks_late_audit_with_full_history`，在新結果發布後、送出前追加假的追溯稽核。舊快照的獨立污染不阻擋新快照；新快照採用來源被標記 `leak_confirmed` 時則拒絕送出，共兩例。

**發現的契約問題與逐項修正**：

1. `src/submit.py`（升為 `submit_v3`）：`continuous.Queue` 在執行時替快照加上 `forecast_scope="snapshot"`，但原始 `questions.jsonl` 沒有此欄位。送出端拿原始快照重建留言時，會把舊快照的首筆合格回答當作整題的固定採用來源，導致已重跑且合法發布的新結果遭到 `adopted inputs no longer match this aggregate` 拒絕。現在對帶有 `cycle_version` 的發布結果，以相同的快照範圍重建留言；凍結的原始快照不改寫。仍傳入完整預測／整合歷史及稽核事件，維持採用來源、機率、留言文字與 hash 的全部檢查；沒有 cycle 標記的既有結果保留原先選取方式。
2. `src/continuous.py`（升為 `continuous_v3`）：原先只要存在未 abandoned 的意圖，佇列就完全略過修訂判定。若文字在意圖建立後修訂，送出端又允許 `text_revised`，就會在明明來得及重跑時送出舊答案。現在對尚無任何 `request_started` 且未 abandoned 的意圖，依既有重跑時間／結構判斷追加 `snapshot_invalidated`；題目仍保持 committed，直到真正的 Submitter 依既有永久拒絕規則寫入 abandoned，下一輪才重新排入。已開始請求的意圖不走此路徑；來不及重跑的純文字修訂不因此作廢。共用同一修訂判斷，且舊快照已作廢時不再次追加相同事件。
3. `src/continuous.py` 的政策版本相容性：行為事件升版後，仍接受原先的 `continuous_v2` 政策，亦接受 `continuous_v3`；避免只因程式升版就拒絕既有凍結預算窗口。原有政策 hash、不可變註冊、窗口重疊及額度檢查均保留，既有政策不須重寫版本或重新註冊。
4. `tests/test_m3_integration.py`：重用既有假 adapter、假傳輸回執與 post 建構方式。增加完整傳輸呼叫追蹤與可指定第幾次帳號讀取失敗；六份設定均複製到測試暫存目錄，改模式、核准 bot ID、停用檔及場地只影響該測試。假輪詢使用真正的快照建構及追加函式，確保模型與送出端看到同一份題目內容。

`src/cycle.py`、既有測試及其預期均未修改。未放寬送出前檢查或停用開關，未更動 prompt、模型參數、整合公式或預算政策。依 AGENTS.md 與前兩份任務的審查紀錄，版本與行為變更先記於本回報，PLAN §16／文件版本由協調者整合，未自行修改 PLAN。

**假設與保守選擇**：

- 未開始請求的意圖遇修訂時，不提前把題目移出 committed，也不由佇列偽造 abandoned。因既有週期順序是先 queue／scheduler、後 submit，修訂當輪由 submit 放棄舊意圖，下一輪才能重跑；若下一輪已來不及，沿用原本截止規則，不能為趕送而繞過凍結或時間檢查。
- `cycle_version` 視為主程式發布紀錄的標記，用來恢復原有快照範圍；不是模型可指定的送出目標。測試涵蓋這項修正後仍會拒絕新來源的延遲稽核污染。
- 整合測試只啟用一條假的 GPT 線，以集中驗證週期與送出契約；不代表真實三線 preflight、額度或 trial 上線驗收。傳輸欄位、回執及讀回假設沿用 M3-W1 的 `FakeTransport`／V15 契約，沒有新增真實傳輸層。
- 結構修訂的選項案例是 binary 變為帶 A／B 選項的 multiple_choice；截止時間案例獨立測試。文字回退案例先保留尚未發布的 local final；結構阻擋案例則特別使用已發布結果，驗證送出端確實尊重作廢事件。
- 所有暫存目錄均放在 clone 的 `scratch/test-tmp`。只對新增整合測試的假 adapter 注入暫存目錄，不改正式工作目錄隔離檢查或既有測試 fixture。
