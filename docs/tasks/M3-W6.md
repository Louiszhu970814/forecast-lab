# M3-W6：週期與送出的整合測試

- 執行：GPT（代理開發模式，D56）
- 審查：Claude
- 依賴：M3-W1（`submit.py`，`submit_v2`）、M3-W2（`cycle.py`、`continuous.py`，`cycle_v2`／`continuous_v2`）
- 需要閱讀：`docs/tasks/M3-W1.md`、`docs/tasks/M3-W2.md`（兩者的規格、執行回報與審查紀錄）、PLAN §3.2、§3.6

## 為什麼需要

M3-W1 與 M3-W2 是平行開發的。各自的測試都以假的對方代替：`test_cycle.py` 用假的 `submit`，`test_submit.py` 自行寫入整合紀錄與佇列事件。兩者之間的契約從來沒有在同一個流程中實際跑過，包括 `cycle.publish()` 產生的 `submission_eligible = true` 整合結果與留言、`question_queue.jsonl` 的 `snapshot_invalidated`、`submissions.jsonl` 的 `intent`／`abandoned`。

## 目標

新增 `tests/test_m3_integration.py`：以 `cycle.run_cycle` 跑一或多個週期，並把真正的 `submit.Submitter` 接上去，取代假的 `submit`。做法是在測試中以 callable 直接在同一程序內呼叫 `Submitter(root, config_dir=<暫存設定>, transport=<假傳輸層>).run()`。輪詢、adapter、時鐘、傳輸層都使用假的；不連網、不呼叫模型 CLI。

## 情境（每一項至少一個測試）

1. **local 模式**：一個週期完成後，每一筆已發布的整合結果都只產生一筆 `dry_run`；假傳輸層收不到任何呼叫（包括讀取）。原本 `submission_eligible = false` 的 local 最終整合只留下一筆 `rejected_precheck`，第二個週期也不重複寫入。
2. **trial 模式，正常送出**：暫存設定中的 `submit_mode.json` 為 `trial`、`approved_bot_id` 已設定，場地為試驗場地。假傳輸層依序收到預測與留言的寫入，帳冊依序出現 `intent` → `request_started` → `forecast_ok` → `request_started` → `comment_ok`。下一個週期不再送出同一題，佇列也把該題當作已送出。
3. **發布後、建立意圖前修訂**：第一個週期發布後讓 `submit` 不執行或因暫時原因拒絕（例如 `STOP_SUBMIT`），接著題目內容修訂，而且時間來得及重跑。第二個週期作廢舊快照並重排第 1 層；`submit` 不送出舊快照的結果，改送出新快照的結果。
4. **建立意圖後、開始請求前修訂**：意圖已建立，但預測請求尚未開始（例如假傳輸層的帳號讀取暫時失敗）。之後題目修訂，舊意圖記為 `abandoned`，`committed_questions()` 不再凍結該題，新快照可以重新排入並建立新的意圖。
5. **預測已開始、結果未知時修訂**：舊意圖只做對帳，不被 `abandoned`，該題維持凍結，不以新快照重送。
6. **文字修訂來不及重跑**：舊快照的結果在送出紀錄中標記 `text_revised`，且帳冊中有 `revision_fallback = true` 的整合結果；結構修訂（選項或截止時間改變）來不及重跑時不送出。

## 規則

- 整合測試發現兩個模組的契約不一致時，以 PLAN 與兩份任務說明的審查紀錄為準，做最小的修正，並在回報中逐項說明修了什麼、為什麼。修正 `submit.py`、`cycle.py`、`continuous.py` 都可以，但不得放寬任何送出前檢查或停用開關。
- 不修改既有測試的預期，除非它與 PLAN 矛盾；若需要修改，在回報中說明。
- 不修改 `config/` 下的正式設定；測試一律在暫存資料夾建立自己的設定。

## 驗收條件

- 上述六個情境都有測試並通過。
- 完整測試 `.venv/bin/python -m pytest -q` 全部通過；在沙箱中因 `TMPDIR` 位於 clone 內而失敗的既有隔離測試，請列出名稱，不要修改。
- 不連網、不呼叫模型 CLI、不安裝 launchd。
